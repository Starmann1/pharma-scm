# PostgreSQL Migration Phase 0 Baseline

## Scope

Phase 0 is a non-invasive discovery and baseline phase for migrating the v1.1 target from MySQL to PostgreSQL.

No live database connection was opened. No MySQL schema, data, scripts, or runtime configuration were modified.

The current v1 branch remains MySQL-based. PostgreSQL migration work is scoped to the future v1.1 upgrade path only.

## Current Workspace State

- Current branch: `v1/jade-langchain4j`
- Existing untracked file observed before this phase: `papers_mas.json`
- Build file: `pom.xml`
- Active database pool implementation: HikariCP through `DatabaseService`
- Current JDBC driver dependency: MySQL Connector/J
- Current local env file: `.env`

Security note: `.env` contains live-looking database credentials and an API key. The values are intentionally not copied into this document. These secrets should be rotated before production use and should not be committed.

## Phase 0 Safety Rules

1. Do not modify the existing MySQL database.
2. Do not rewrite or delete `database.sql` or existing MySQL migration scripts during Phase 0.
3. Do not change v1 runtime behavior.
4. Do not replace the MySQL dependency on the current v1 branch.
5. Keep PostgreSQL scripts, configuration, and validation artifacts isolated for v1.1.
6. HikariCP remains the only allowed connection pool.
7. UI and agents must continue to access persistence through services/repositories, not direct JDBC.

## MySQL-Specific Constructs To Convert

The current SQL uses several MySQL-specific constructs that must not be copied directly into PostgreSQL:

| MySQL construct | PostgreSQL replacement |
| --- | --- |
| `CREATE DATABASE IF NOT EXISTS` | Create database outside application migration or use deployment provisioning. |
| `USE pharma_ims` | Use JDBC URL/database selection. |
| `SET FOREIGN_KEY_CHECKS = 0/1` | Load in dependency order or use deferrable constraints where justified. |
| `AUTO_INCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` or `GENERATED ALWAYS AS IDENTITY`. |
| `ON UPDATE CURRENT_TIMESTAMP` | Application-managed `updated_at` or PostgreSQL trigger. |
| `TINYINT(1)` | `BOOLEAN`. |
| `LONGTEXT` | `TEXT`. |
| `LAST_INSERT_ID()` | JDBC generated keys or `INSERT ... RETURNING id`. |
| `SET @variable` | CTEs, explicit IDs, or application-controlled generated keys. |
| `NOW()` | `CURRENT_TIMESTAMP` or `now()`. |
| `CURDATE()` | `CURRENT_DATE`. |
| `ON DUPLICATE KEY UPDATE` | `ON CONFLICT (...) DO UPDATE`. |
| `ALTER TABLE ... MODIFY COLUMN` | `ALTER TABLE ... ALTER COLUMN ... TYPE ...`. |
| `UPDATE ... JOIN` | `UPDATE ... SET ... FROM ... WHERE ...`. |

## Application Code Findings

### HikariCP

`DatabaseService` initializes HikariCP and obtains connections through `ds.getConnection()`. This is the correct pooling boundary to preserve.

### MySQL Driver Dependency

`pom.xml` currently depends on MySQL Connector/J. v1.1 will need a PostgreSQL JDBC driver in its own upgrade branch. v1 should retain MySQL.

### Direct MySQL Connections Outside HikariCP

The following Swing UI classes contain direct `DriverManager.getConnection(...)` MySQL usage and hardcoded credentials:

- `src/main/java/pharma/gui/CreateGRNDialog.java`
- `src/main/java/pharma/gui/ViewGRNDetailsDialog.java`

This violates the HikariCP-only requirement and must be fixed before or during the v1.1 migration. For v1, do not change these until a separate safe fix is approved.

### MySQL Dialect In Java SQL

`DatabaseService` contains MySQL-specific SQL, including:

- `ON DUPLICATE KEY UPDATE`
- `CURDATE()`
- `DATE(...)` timestamp filtering
- `UPDATE ... JOIN`
- mixed-case table references
- startup schema patching with MySQL DDL

These must be isolated and converted for v1.1 PostgreSQL.

## Phase 0 Risk Register

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Mixed-case table names | PostgreSQL identifier mismatch | Normalize to lowercase snake_case in v1.1. |
| MySQL-only DDL and DML | Migration scripts fail | Build clean PostgreSQL DDL instead of editing MySQL scripts in place. |
| Hardcoded direct JDBC credentials in UI | Security and HikariCP violation | Replace with service/repository calls in v1.1. |
| Single large `database.sql` contains schema plus seed plus later changes | Hard to replay safely | Split PostgreSQL migration into versioned schema, reference data, sample data, and patch scripts. |
| Existing v1 must remain MySQL | Regression risk | Keep v1 untouched and create v1.1-specific PostgreSQL artifacts. |
| Agent workflows depend on DB queries | Hidden dialect coupling | Run agent regression after PostgreSQL repository conversion. |
| `.env` contains secrets | Credential leakage risk | Do not commit `.env`; rotate secrets before deployment. |
